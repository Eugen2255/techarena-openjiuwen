# Харнесс TechArena 2026 на openJiuwen

Харнесс кодового агента: получает каталог со 100 задачами, решает их моделями через LLM-прокси
организаторов и записывает ответ в `answer.txt` каждой задачи.

Разделы, которые требует регламент: [сборка и запуск](#сборка-и-запуск),
[оценка расхода токенов](#оценка-расхода-токенов), [поиск невыполнимых задач](#поиск-невыполнимых-задач),
[тренировочный набор и траектории](#тренировочный-набор-и-траектории).

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm -e LLM_BASE_URL -e LLM_API_KEY -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp --cap-drop ALL --security-opt no-new-privileges \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

- Переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY` — адрес и ключ прокси; `BUDGET` — бюджет токенов
  (out + in/10, по умолчанию 100000); `OUT` или `--out` — необязательный файл с решениями (JSON `{task_id: answer}`),
  он перезаписывается после каждой задачи.
- Ответ каждой задачи пишется в `<task>/answer.txt` рядом с `task.json`. Для задачи, признанной невыполнимой,
  файл не создаётся.
- Настройки для экспериментов — переменные `HARNESS_*` (см. `harness/config.py`). На официальном прогоне
  они не передаются, работают значения по умолчанию.
- Локальная разработка: `python scripts/run_dev.py` (см. `START_HERE.md`).

## Как это работает

1. Загружаем все `task.json`.
2. **Быстрый путь:** детерминированные решатели (`harness/fastpath/`) решают задачи, шаблон которых распознан
   целиком, — без LLM и без токенов. Организаторы это разрешили. Сейчас покрыты `data_analysis` (сумма units
   по товару и месяцам), `math` (цепочка операций со складом) и `search` (атрибуты и цепочки связей в `kb/`);
   при любом незнакомом предложении задача уходит дальше. Решатели и сами распознают невыполнимые задачи, если
   условие разобрано, а данных нет: в `math` — неопределённое количество, деление на 0, операция без нужного
   числа (темп без длительности, деление без числа складов); в `data_analysis` — нет файла; в `search` —
   отсутствующий человек или компания, оборванная ссылка, нет поля, однофамильцы, имя без фамилии при нескольких
   людях с таким именем. Тесты: `python -m unittest discover -s tests`.
3. Остальные задачи сортируем по выгодности (`reward / прогноз стоимости`, см. ниже) и решаем в 5 параллельных
   воркерах, **каждую — одним вызовом LLM** через `Model` openJiuwen, без цикла агента (math — моделью
   с рассуждениями, остальное — без них, см. «Выбор модели»):
   - `math`, `data_analysis` (`harness/oneshot.py`): модель присылает короткую программу на Python, харнесс запускает
     её сам и берёт напечатанный ответ. Для CSV в запросе — заголовок, первые строки и явный список колонок;
   - `search` (`harness/oneshot.py`): база знаний целиком в запросе (одна запись — одна строка), ответ — строка
     `ANSWER:`; ответ принимается, только если он буквально есть в базе;
   - `coding` (`harness/coding.py`): исходник модуля и выжимка упавших тестов, в ответе — только исправленные
     функции; харнесс подставляет их и гоняет тесты, при неудаче — ещё один раунд с полным текстом тестов.

   Невыполнимость видна не только со слов модели (`INFEASIBLE`), но и по запуску:
   - `data_analysis`: программа обращается к несуществующей колонке (`KeyError`) и после подсказки со списком
     колонок, или программа сама печатает `INFEASIBLE`; `math`: деление на 0 и после подсказки;
   - `coding`, до вызова LLM: противоречивые тесты — один вызов функции модуля с литералами ожидается с разными
     значениями, значение и ожидается, и запрещено, `assertNotEqual(f(1), f(1))`.

   Тогда `answer.txt` не создаётся.
4. Если один вызов не справился (нет кода, программа дважды падает, ответа нет в базе, непривычная раскладка
   задачи), задачу решает цикл агента: `ReActAgent` openJiuwen с инструментом `bash` в рабочей папке задачи.
   Ответ берём из строки `ANSWER: ...`, проверяем без LLM (тесты, формат числа) и сразу записываем.
5. **Бюджет не пересекаем ни на один вызов.** Остатка прокси не сообщает: расход считают организаторы и при
   исчерпании 100K останавливают прогон, засчитывая решённое к этому моменту. Поэтому перед каждым вызовом LLM
   резервируем его худшую стоимость: оценка входа + потолок выхода
   (`max_tokens`). Вызов не начинается, если потраченное + резервы идущих вызовов + его резерв больше бюджета.
   Если мешают только резервы параллельных вызовов, вызов ждёт их окончания. Задачу, оценка стоимости которой
   больше остатка, не начинаем; потолок на задачу обрывает дорогие задачи. Ответы пишутся сразу и атомарно,
   поэтому всё решённое до обрыва остаётся. Сторож времени останавливает прогон за 5 минут до часового лимита.
6. Запросы к LLM идут не чаще 50 в минуту и не больше 3 одновременно (лимиты NeuralDeep — 60 в минуту и 3 одновременных
   на аккаунт). При ответах 429/5xx и таймаутах делаем до трёх повторов с паузой: openJiuwen сам не повторяет.

### Выбор модели

`math` решает `qwen3.8-27b` с рассуждениями, остальные типы — `qwen3.8-27b-noreason` (`harness/config.py`,
`solver.choose_model`).

На задачах нового вида (другие сюжеты и формулировки, см. «Поиск невыполнимых задач») модель без рассуждений
в math путает отданную и оставшуюся часть: «half of the books are given away (if the number is odd, the extra one
stays)» превращает в `x // 2`, «one third … are moved to another site» — в `x // 3`. Сравнение на 69 math-задачах,
которые не берёт быстрый путь (60 нового вида и 9 перефразировок):

| Вариант | Верно | Токены |
|---|---|---|
| `qwen3.8-27b-noreason` | 58/69 | 5 708 |
| `-noreason` + промпт «одно предложение — одна строка с комментарием» | 62/69 | 10 419 |
| **`qwen3.8-27b` с рассуждениями** | **68/69** | 17 850 |

Модель с рассуждениями втрое дороже, но на ~25 math-задач финала это 4–5K токенов из 100K, а баллы важнее
токенов. В data_analysis, search и coding модель без рассуждений решила все 180 задач нового вида (двух наборов),
поэтому там её не меняем. Потолок выхода моделей с рассуждениями — 4096 токенов (`HARNESS_MAX_OUTPUT_TOKENS_REASONING`):
рассуждения входят в выход.

Прежнее сравнение на задачах в стиле примеров (там все модели решили всё без ошибок, различались расход и скорость):

| Модель | Токены, 71 задача (сид 2) | Токены, 37 задач (сид 3) | Время задач (сид 3) |
|---|---|---|---|
| **qwen3.8-27b-noreason** | **5168** | **2625** | **172 с** |
| qwen3.6-35b-a3b-noreason | 7222 (+40%) | 3861 (+47%) | 298 с |
| qwen3.8-27b (с рассуждениями) | — | 7510 (×2,9) | 320 с |
| qwen3.6-35b-a3b (с рассуждениями) | — | 22 337 (×8,5) | 562 с |

`qwen3.6-35b-a3b-noreason` многословнее и при этом медленнее, а `qwen3.6-35b-a3b` с рассуждениями — в 8 раз
дороже.

## Надёжность и безопасность

**Время.** Часовой лимит считается от старта процесса (`harness/__init__.py: STARTED_AT`). За 5 минут до него
харнесс перестаёт брать новые задачи, доводит начатые и выходит с кодом 0. На SIGTERM (его шлёт `timeout`
организаторов) — то же самое: в контейнере харнесс работает как PID 1, и без обработчика сигнал был бы
проигнорирован до SIGKILL. Причина остановки (`time limit`, `SIGTERM`, `token budget`,
`LLM proxy stopped answering`) пишется в итоговую сводку.

**Сеть и файлы.** При запуске ничего не скачивается: зависимости и словари `tiktoken` — в образе, логи
openJiuwen перенаправлены в консоль. Харнесс пишет только в `/tmp` (рабочие папки, программы модели, траектории)
и в папки задач (`answer.txt` и исправленные исходники coding). При старте проверяет, что в папки задач можно
писать: с `--cap-drop ALL` root в контейнере пишет только туда, где это разрешают биты доступа.

**Что выполняет агент.** Код, присланный моделью (программы для math и data_analysis, исправления coding,
команды bash в цикле агента), выполняется:
- в рабочей папке задачи или во временной папке в `/tmp`;
- с таймаутом (`HARNESS_COMMAND_TIMEOUT`, 60 с) и с обрезкой вывода;
- без ключа прокси и других секретов в окружении (`harness/shell.py` убирает `LLM_*` и переменные с `KEY`,
  `TOKEN`, `SECRET`, `PASSWORD`).

Изоляцию контейнера (сеть только до прокси, read-only, без capabilities) обеспечивают флаги запуска
организаторов. Ключ API в репозиторий и образ не попадает: он приходит в `LLM_API_KEY` при запуске.

**Проверки без LLM в CI** (`.github/workflows/ci.yml`): модульные тесты, быстрый путь на примерах и
сгенерированных задачах, чистая сборка образа без кеша с замером времени и размера, запуск с флагами регламента
без сети.

## Оценка расхода токенов

**Факт.** Расход считаем по полю `usage` каждого ответа модели: `выходные + входные / 10` (`harness/meter.py`).
У NeuralDeep токены рассуждений уже входят в `completion_tokens`.

**Прогноз до запуска** (`harness/estimator.py`) — только по `task.json` и файлам задачи, без LLM и без запуска
кода задачи:
1. **Маршрут** — теми же проверками, что у харнесса: задачу возьмёт быстрый путь (прогноз 0), тесты coding
   противоречат друг другу — тоже 0; иначе задача решается одним вызовом (`coding`, `oneshot:<тип>`) или циклом
   агента.
2. **Стоимость внутри маршрута** — линейная модель по статическим признакам (длина инструкции, число файлов,
   размер модуля, число проверок и т.п.). Модель на каждом маршруте выбирается по ошибке leave-one-out между
   «средним», одним признаком и всеми признаками (ridge-регрессия). Параметры — `harness/estimator_params.json`.
3. **Верхняя оценка** = точечная × 90-й процентиль отношения «факт/прогноз» — на случай штрафа за недооценку.

Харнесс использует прогноз для порядка задач (больше баллов на токен — раньше) и чтобы не начинать задачу,
на которую не хватит бюджета; в траектории пишутся маршрут, прогноз и верхняя оценка рядом с фактом.

**Точность** — проверка на отложенном прогоне задач нового вида (сид 22: 120 задач, 112 с вызовами LLM), обучение
на трёх других прогонах (330 задач). Суммарный прогноз — 18 568 токенов при факте 18 606:

| | MAE на задачу | MAPE | доля недооценок |
|---|---|---|---|
| все задачи, точечный прогноз | 24 токена | 17% | 41% |
| все задачи, верхний прогноз | 72 токена | 52% | 4% |
| только задачи с LLM, точечный | 26 токенов | 17% | 44% |

Нули быстрого пути и противоречивых тестов предсказываются точно. Итоговые параметры подобраны на четырёх прогонах
текущей версии (450 задач, 304 с вызовами LLM): два набора нового вида, набор в стиле примеров и 60 невыполнимых
задач новых видов.

```bash
python scripts/estimate.py <tasks_dir> [--json predictions.json]       # прогноз для набора задач
python scripts/fit_estimator.py --dataset trajectories/estimator_dataset.jsonl --write   # подбор параметров
python scripts/fit_estimator.py runs/<A> runs/<B> --holdout runs/<C>    # подбор по прогонам с проверкой
```

Оценщик предсказывает расход **нашего** харнесса, поэтому после изменений в харнессе параметры нужно подобрать
заново: прогнать сгенерированные наборы (`scripts/run_dev.py --tasks ...`) и запустить `fit_estimator.py`.

## Поиск невыполнимых задач

Невыполнимая задача — та, которую нельзя точно решить по имеющимся данным. Баллов за её распознавание нет, а ответ
на неё не штрафуется (встреча с организаторами 09.11): выгода от распознавания — только сэкономленные токены.
Ошибочно пропущенная выполнимая задача, наоборот, теряет баллы, поэтому правила без LLM нарочно осторожные.
Для задачи, признанной невыполнимой, `answer.txt` не создаётся. Распознаём в три слоя, от дешёвого к дорогому:

1. **Без LLM, по разобранному условию** (быстрый путь, `harness/fastpath/`): решатель разобрал условие целиком,
   а нужных данных нет. В `math` — неопределённое количество, деление на 0, операция без нужного числа (темп без
   длительности, деление без числа складов); в `data_analysis` — нет файла из условия; в `search` — человека или
   компании нет в базе, ссылка ведёт в никуда, у записи нет нужного поля, однофамильцы, имя без фамилии при
   нескольких людях с таким именем.
2. **Без LLM, противоречивые тесты coding** (`coding.contradictory_tests`): один вызов функции модуля с литералами
   ожидается с разными значениями, значение и ожидается, и запрещено, `assertNotEqual(f(1), f(1))`. Переменные,
   методы объектов, вызовы без аргументов и функции с состоянием правило не трогает.
3. **С LLM**: модель отвечает `INFEASIBLE` (промпты запрещают додумывать недостающее число, файл, колонку или
   запись, но разрешают величины, выводимые из данных, — например, выручку как units × price); программа модели
   печатает `INFEASIBLE`; программа обращается к несуществующей колонке или делит на 0 и после подсказки.
   Ответ модели проверяется без LLM: в `search` он принимается, только если есть в базе, в `coding` — только если
   проходят тесты.

**Проверка на ложные срабатывания.** Организаторы предупредили, что в финале будут «новые и другие вопросы», а не
шаблоны примеров с другими числами. Поэтому, кроме наборов в стиле примеров, генератор делает задачи нового вида
(`--novel-share 1.0`): другие сюжеты math; другие вопросы и схемы CSV (выручка без расшифровки, «orders cost more
than 500», колонка status, таблица сотрудников); база знаний связным текстом, вопросы-подсчёты и сравнения в search;
тесты с переменными, from-импортом и классами в coding. Прежние правила без LLM на 120 таких выполнимых задачах
ошиблись 30 раз: 20 тестов coding с переменными и объектами сочли противоречивыми, а правило по словам вопроса
data_analysis («total revenue», «cost», «returned» при колонке status) отбросило 10 задач. Правило для data_analysis
удалено, правило для coding сужено. Теперь `scripts/check_fastpath.py` даёт 0 неверных ответов и 0 ложных
«невыполнима» на всех наборах, включая 320 задач нового вида; это проверяет и CI.

Прогоны с моделью (текущая версия; траектории — в `trajectories/raw/`):

| Набор | Выполнимые решены | Баллы | Невыполнимые пропущены | Токены |
|---|---|---|---|---|
| новый вид, сид 21 (120 задач) | 120/120 | 345/345 | — | 18 358 |
| новый вид, сид 22 (120 задач) | 118/120 | 370/380 | — | 18 606 |
| в стиле примеров, сид 2 (150, из них 45 невыполнимых) | 105/105 | 312/312 | 41/45 | 9 083 |
| невыполнимые новых видов (60) | — | — | 49/60 | 2 319 |

Ни одна выполнимая задача не объявлена невыполнимой. Две ошибки — неверные ответы модели в math. На 15 невыполнимых
задач data_analysis модель всё же ответила: досчитала то, чего нет в данных (например, возвраты по файлу продаж).
Штрафа за это нет, цена — около 115 токенов на задачу. Наши примеры невыполнимых задач — `tasks_custom/` (правильно —
не создать ни одного `answer.txt`), гипотезы — `docs/pipeline.md`, раздел 5.

## Тренировочный набор и траектории

Готовых данных организаторы не дают, поэтому задачи генерируем сами: `scripts/generate_tasks.py` создаёт задачи
4 типов в формате организаторов — шаблоны из примеров, перефразировки, задачи нового вида (`--novel-share`) и
невыполнимые варианты (неизвестное количество, деление на 0, нет файла или колонки, нет человека в базе,
оборванная ссылка, однофамильцы, противоречивые тесты). Для coding генерируются скрытые тесты.
`scripts/check_fastpath.py` проверяет всё, что решается без LLM, `scripts/run_dev.py --tasks tasks_generated` —
весь харнесс в Docker.

Каждый прогон пишет `trajectories_*.jsonl` (папка `HARNESS_LOG_DIR`): задача, решатель, маршрут, модель, токены
(вход, выход, рассуждения, стоимость), время, ответ, признак невыполнимости, результат локальной проверки,
прогноз и верхняя оценка стоимости.

Собранные траектории лежат в `trajectories/`:
- `raw/` — траектории четырёх прогонов текущей версии (результаты — в таблице раздела «Поиск невыполнимых задач»):
  два набора нового вида по 120 задач, набор в стиле примеров (150 задач) и 60 невыполнимых задач новых видов;
- `estimator_dataset.jsonl` — обучающая выборка оценщика: маршрут, статические признаки задачи и фактический
  расход (450 записей). Траектории прежних версий харнесса — в истории git.

Наборы воспроизводятся текущим генератором: новый вид — `--count 120 --seed 21` (и `--seed 22`)
`--novel-share 1.0 --infeasible-share 0`; в стиле примеров — `--count 150 --seed 2 --paraphrase-share 0.6
--infeasible-share 0.3`; невыполнимые новых видов — `--count 60 --seed 11 --infeasible-share 1.0
--infeasible-kinds missing_duration missing_parts returns_not_tracked missing_column_phrasing unknown_field
