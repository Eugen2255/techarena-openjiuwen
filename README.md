# Харнесс TechArena 2026 на openJiuwen

Харнесс кодового агента: получает каталог со 100 задачами, решает их моделями через LLM-прокси
организаторов и записывает ответ в `answer.txt` каждой задачи.

> Регламент требует описать в README сборку и запуск, способ оценки расхода, поиск невыполнимых
> задач и собранные траектории. Разделы с пометкой **TODO** заполняем по ходу работы.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm -e LLM_BASE_URL -e LLM_API_KEY -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp --cap-drop ALL --security-opt no-new-privileges \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

- Переменные окружения: `LLM_BASE_URL`, `LLM_API_KEY` — адрес и ключ прокси; `BUDGET` — бюджет токенов
  (out + in/10, по умолчанию 100000); `OUT` или `--out` — необязательный файл с решениями (JSON `{task_id: answer}`),
  он перезаписывается после каждой задачи.
- Ответ каждой задачи пишется в `<task>/answer.txt` рядом с `task.json`. Для задачи, признанной невыполнимой,
  файл не создаётся.
- Настройки для экспериментов — переменные `HARNESS_*` (см. `harness/config.py`). На официальном прогоне
  они не передаются, работают значения по умолчанию.
- Локальная разработка: `python scripts/run_dev.py` (см. `START_HERE.md`).

## Как это работает

1. Загружаем все `task.json`.
2. **Быстрый путь:** детерминированные решатели (`harness/fastpath/`) решают задачи, шаблон которых распознан
   целиком, — без LLM и без токенов. Организаторы это разрешили. Сейчас покрыты `data_analysis` (сумма units
   по товару и месяцам), `math` (цепочка операций со складом) и `search` (атрибуты и цепочки связей в `kb/`);
   при любом незнакомом предложении задача уходит дальше. Решатели и сами распознают невыполнимые задачи, если
   условие разобрано, а данных нет: в `math` — неопределённое количество, деление на 0, операция без нужного
   числа (темп без длительности, деление без числа складов); в `data_analysis` — нет файла; в `search` —
   отсутствующий человек или компания, оборванная ссылка, нет поля, однофамильцы, имя без фамилии при нескольких
   людях с таким именем. Тесты: `python -m unittest discover -s tests`.
3. Остальные задачи сортируем по выгодности (`reward / прогноз стоимости`, см. ниже) и решаем в 5 параллельных
   воркерах, **каждую — одним вызовом LLM** через `Model` openJiuwen, без цикла агента:
   - `math`, `data_analysis` (`harness/oneshot.py`): модель присылает короткую программу на Python, харнесс запускает
     её сам и берёт напечатанный ответ. Для CSV в запросе — заголовок, первые строки и явный список колонок;
   - `search` (`harness/oneshot.py`): база знаний целиком в запросе (одна запись — одна строка), ответ — строка
     `ANSWER:`; ответ принимается, только если он буквально есть в базе;
   - `coding` (`harness/coding.py`): исходник модуля и выжимка упавших тестов, в ответе — только исправленные
     функции; харнесс подставляет их и гоняет тесты, при неудаче — ещё один раунд с полным текстом тестов.

   Невыполнимость видна не только со слов модели (`INFEASIBLE`), но и без неё — это важно, потому что дешёвая модель
   склонна молча додумывать недостающее (1 день, 2 склада, «скидка» = выручка):
   - `data_analysis`, до вызова LLM: вопрос о величине, событии или понятии, которых нет среди колонок и которые
     не определены в самом вопросе («total discount», «were returned», «profit», «customer»);
   - `data_analysis`, после запуска программы: обращение к несуществующей колонке (`KeyError`) или программа
     сама печатает `INFEASIBLE`;
   - `coding`, до вызова LLM: противоречивые тесты — разные ожидания одного вызова, ожидание и запрет одного
     значения, `assertNotEqual(f(1), f(1))` для детерминированной функции.

   Тогда `answer.txt` не создаётся.
4. Если один вызов не справился (нет кода, программа дважды падает, ответа нет в базе, непривычная раскладка
   задачи), задачу решает цикл агента: `ReActAgent` openJiuwen с инструментом `bash` в рабочей папке задачи.
   Ответ берём из строки `ANSWER: ...`, проверяем без LLM (тесты, формат числа) и сразу записываем.
5. **Бюджет не пересекаем ни на один вызов.** После исчерпания 100K прокси перестаёт отвечать и запуск принудительно
   завершают, поэтому перед каждым вызовом LLM резервируем его худшую стоимость: оценка входа + потолок выхода
   (`max_tokens`). Вызов не начинается, если потраченное + резервы идущих вызовов + его резерв больше бюджета.
   Если мешают только резервы параллельных вызовов, вызов ждёт их окончания. Задачу, оценка стоимости которой
   больше остатка, не начинаем; потолок на задачу обрывает дорогие задачи. Ответы пишутся сразу и атомарно,
   поэтому всё решённое до обрыва остаётся. Сторож времени останавливает прогон за 5 минут до часового лимита.
6. Запросы к LLM идут не чаще 50 в минуту и не больше 3 одновременно (лимиты NeuralDeep — 60 в минуту и 3 одновременных
   на аккаунт). При ответах 429/5xx и таймаутах делаем до трёх повторов с паузой: openJiuwen сам не повторяет.

### Выбор модели

Модель по умолчанию — `qwen3.8-27b-noreason`. Сравнение на задачах, где вызывается LLM (подмножества
сгенерированных наборов; все модели решили их без ошибок, различались расход и скорость):

| Модель | Токены, 71 задача (сид 2) | Токены, 37 задач (сид 3) | Время задач (сид 3) |
|---|---|---|---|
| **qwen3.8-27b-noreason** | **5168** | **2625** | **172 с** |
| qwen3.6-35b-a3b-noreason | 7222 (+40%) | 3861 (+47%) | 298 с |
| qwen3.8-27b (с рассуждениями) | — | 7510 (×2,9) | 320 с |
| qwen3.6-35b-a3b (с рассуждениями) | — | 22 337 (×8,5) | 562 с |

`qwen3.6-35b-a3b-noreason` многословнее и при этом медленнее; модели с рассуждениями точнее не стали, а стоят
в 3–8 раз дороже (рассуждения входят в выходные токены). Для моделей с рассуждениями нужен больший потолок
выхода (`HARNESS_MAX_OUTPUT_TOKENS=8192`).

## Надёжность и безопасность

**Время.** Часовой лимит считается от старта процесса (`harness/__init__.py: STARTED_AT`). За 5 минут до него
харнесс перестаёт брать новые задачи, доводит начатые и выходит с кодом 0. На SIGTERM (его шлёт `timeout`
организаторов) — то же самое: в контейнере харнесс работает как PID 1, и без обработчика сигнал был бы
проигнорирован до SIGKILL. Причина остановки (`time limit`, `SIGTERM`, `token budget`,
`LLM proxy stopped answering`) пишется в итоговую сводку.

**Сеть и файлы.** При запуске ничего не скачивается: зависимости и словари `tiktoken` — в образе, логи
openJiuwen перенаправлены в консоль. Харнесс пишет только в `/tmp` (рабочие папки, программы модели, траектории)
и в папки задач (`answer.txt` и исправленные исходники coding). При старте проверяет, что в папки задач можно
писать: с `--cap-drop ALL` root в контейнере пишет только туда, где это разрешают биты доступа.

**Что выполняет агент.** Код, присланный моделью (программы для math и data_analysis, исправления coding,
команды bash в цикле агента), выполняется:
- в рабочей папке задачи или во временной папке в `/tmp`;
- с таймаутом (`HARNESS_COMMAND_TIMEOUT`, 60 с) и с обрезкой вывода;
- без ключа прокси и других секретов в окружении (`harness/shell.py` убирает `LLM_*` и переменные с `KEY`,
  `TOKEN`, `SECRET`, `PASSWORD`).

Изоляцию контейнера (сеть только до прокси, read-only, без capabilities) обеспечивают флаги запуска
организаторов. Ключ API в репозиторий и образ не попадает: он приходит в `LLM_API_KEY` при запуске.

**Проверки без LLM в CI** (`.github/workflows/ci.yml`): модульные тесты, быстрый путь на примерах и
сгенерированных задачах, чистая сборка образа без кеша с замером времени и размера, запуск с флагами регламента
без сети.

## Оценка расхода токенов

**Факт.** Расход считаем по полю `usage` каждого ответа модели: `выходные + входные / 10` (`harness/meter.py`).
У NeuralDeep токены рассуждений уже входят в `completion_tokens`.

**Прогноз до запуска** (`harness/estimator.py`) — только по `task.json` и файлам задачи, без LLM и без запуска
кода задачи:
1. **Маршрут** — теми же проверками, что у харнесса: задачу возьмёт быстрый путь (прогноз 0), тесты coding
   противоречат друг другу или невыполнимость видна до вызова LLM (`precheck`) — тоже 0; иначе задача решается
   одним вызовом (`coding`, `oneshot:<тип>`) или циклом агента.
2. **Стоимость внутри маршрута** — линейная модель по статическим признакам (длина инструкции, число файлов,
   размер модуля, число проверок и т.п.). Модель на каждом маршруте выбирается по ошибке leave-one-out между
   «средним», одним признаком и всеми признаками (ridge-регрессия). Параметры — `harness/estimator_params.json`.
3. **Верхняя оценка** = точечная × 90-й процентиль отношения «факт/прогноз» — на случай штрафа за недооценку.

Харнесс использует прогноз для порядка задач (больше баллов на токен — раньше) и чтобы не начинать задачу,
на которую не хватит бюджета; в траектории пишутся маршрут, прогноз и верхняя оценка рядом с фактом.

**Точность** (обучение на прогонах сидов 1 и 2, проверка на отложенном прогоне сида 3, 100 задач;
суммарный прогноз 2677 токенов при факте 2650):

| | MAE на задачу | MAPE | доля недооценок |
|---|---|---|---|
| все задачи, точечный прогноз | 7 токенов | 35% | 14% |
| все задачи, верхний прогноз | 11 токенов | 68% | 4% |
| только задачи с LLM, точечный | 25 токенов | 35% | 48% |

Нули быстрого пути и проверок до вызова LLM предсказываются точно. Решение одним вызовом сделало расход
предсказуемее: с циклом агента та же проверка давала MAE 25 токенов на задачу и −21% по сумме. Итоговые
параметры подобраны на четырёх прогонах (410 задач, 118 с вызовами LLM).

```bash
python scripts/estimate.py <tasks_dir> [--json predictions.json]       # прогноз для набора задач
python scripts/fit_estimator.py --dataset trajectories/estimator_dataset.jsonl --write   # подбор параметров
python scripts/fit_estimator.py runs/<A> runs/<B> --holdout runs/<C>    # подбор по прогонам с проверкой
```

Оценщик предсказывает расход **нашего** харнесса, поэтому после изменений в харнессе параметры нужно подобрать
заново: прогнать сгенерированные наборы (`scripts/run_dev.py --tasks ...`) и запустить `fit_estimator.py`.

## Тренировочный набор и траектории

Готовых данных организаторы не дают, поэтому задачи генерируем сами: `scripts/generate_tasks.py` создаёт задачи
4 типов в формате организаторов — шаблоны из примеров, перефразировки и невыполнимые варианты (неизвестное
количество, деление на 0, нет файла или колонки, нет человека в базе, оборванная ссылка, однофамильцы,
противоречивые тесты). Для coding генерируются скрытые тесты. `scripts/check_fastpath.py` проверяет быстрый путь
без LLM, `scripts/run_dev.py --tasks tasks_generated` — весь харнесс в Docker.

Каждый прогон пишет `trajectories_*.jsonl` (папка `HARNESS_LOG_DIR`): задача, решатель, маршрут, модель, токены
(вход, выход, рассуждения, стоимость), время, ответ, признак невыполнимости, результат локальной проверки,
прогноз и верхняя оценка стоимости.

Собранные траектории лежат в `trajectories/`:
- `raw/` — траектории четырёх прогонов на сгенерированных наборах (`qwen3.8-27b-noreason`, решение одним
  вызовом): сиды 1, 2, 3 (350 задач) и набор из 60 невыполнимых задач новых видов. Результат: 265/265
  выполнимых решены, 145/145 невыполнимых пропущены, 11 031 токен на все 410 задач;
- `estimator_dataset.jsonl` — обучающая выборка оценщика: маршрут, статические признаки задачи и фактический
  расход (410 записей). Траектории прежних версий харнесса (с циклом агента) — в истории git.

Наборы задач воспроизводятся командой `scripts/generate_tasks.py --seed N` генератором из коммита `dd5c535`
(в более поздних версиях добавлены новые виды невыполнимых задач, и тот же сид даёт другой набор):
сид 1 — 100 задач по умолчанию; сид 2 — 150 задач, `--paraphrase-share 0.6 --infeasible-share 0.3`;
сид 3 — 100 задач по умолчанию. Набор новых видов — текущим генератором: `--count 60 --seed 11
--infeasible-share 1.0 --infeasible-kinds missing_duration missing_parts returns_not_tracked
missing_column_phrasing unknown_field absent_company ambiguous_first_name impossible_assert`.
