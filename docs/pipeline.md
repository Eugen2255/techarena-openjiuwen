## 1. Что сдаём

Git-репозиторий (GitHub или GitFlic). Если он приватный, нужно дать доступ `promsoft` и `madrugado`, иначе работу не проверят. В репозитории:

- `Dockerfile` харнесса на базе openJiuwen последней версии (сейчас `openjiuwen==0.1.20.post3`; перед сдачей проверить, не вышла ли новая);
- `/app/run_agent.py` — точка входа;
- все файлы, нужные для сборки и работы;
- `README.md`: сборка и запуск, как оцениваем расход токенов, как ищем невыполнимые задачи, собранные траектории.

Как запускают:

```
docker run --rm --network hack-net -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges --cpus 8 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

| Ограничение | Значение |
|---|---|
| Время работы | 1 час на весь прогон |
| Бюджет | **ровно 100K** токенов (out + in/10); после исчерпания прокси перестаёт отвечать |
| LLM | `LLM_BASE_URL=https://api.neuraldeep.ru/v1` — тот же NeuralDeep, что при разработке; лимит 60 запросов в минуту |
| CPU | 8 логических ядер Xeon E5-2696 v4 |
| Параллельность | до 5 сессий агента |
| Файловая система | только чтение. Писать можно в `/tmp` (2 ГБ) и `/data/tasks` |
| Сеть | только прокси организаторов (`LLM_BASE_URL`), ничего не скачивать при запуске |
| Образ | меньше 4 ГБ, сборка не дольше 1000 с, версии и тег базового образа зафиксированы |
| Репозиторий | меньше 100 МБ без `.git`, без API-ключей |
| Модели | только 4 модели через прокси, локальные нейросети запрещены (регрессия и бустинг можно) |

Этапы оценки:
1. Проверка образа на безопасность с помощью LLM.
2. Сборка.
3. Отборочный прогон: **обе** из 2 выполнимых задач должны быть решены.
4. Полный прогон на 100 задачах.

При равенстве баллов выигрывает тот, кто потратил меньше токенов.

## 2. Что видно по примерам задач

Все 8 примеров сгенерированы по шаблонам. Их 4 типа:

| Тип | Что нужно сделать | Проверка | Как решать дёшево |
|---|---|---|---|
| `math` | Цепочка операций со складом (поделить с округлением вниз, удвоить, отгрузить N в день…) | `exact_int` | Одна команда `python3 -c`; модель переводит текст в выражение |
| `data_analysis` | Сумма `units` по товару и диапазону месяцев в `sales.csv` (20–300 строк) | `exact_int` | Одна pandas/csv-команда, файл в контекст не грузить: хватит заголовка и пары строк |
| `search` | Вопрос по базе `kb/*.md` (~36 файлов, 48 КБ), бывает в несколько переходов: человек → работодатель → город HQ | `exact_str` | `grep` по имени, затем `cat` найденного файла. Файлы крошечные |
| `coding` | Исправить баги в `mylib.py`, чтобы прошёл `test_mylib.py`. Тесты не трогать, в `answer.txt` записать `DONE` | `unittest` (скрытые тесты) | Сразу дать модели `mylib.py`, тесты и вывод прогона: исправление в один шаг. Баги простые (`-=` вместо `+=`, `<` вместо `>`, `sorted` вместо `reversed`) |

Наблюдения:
- `reward` от 1 до 5 и не зависит от сложности: самый дорогой пример (5) — тривиальная математика.
- В примерах есть поля `expected` и `check`. Они совпадают с честно посчитанным ответом, поэтому годятся как эталон для локальной проверки. В финальном наборе `expected` уберут, а `check`, `reward`, `task_type` останутся.
- У задач `math` **нет папки `workspace`**. Организаторы уточнили: `answer.txt` всегда кладём **рядом с `task.json`**, а не в `workspace`.
- Для `coding` проверка идёт скрытыми тестами. Баг надо исправлять по смыслу функции, а не подгонять под видимые тесты.
- Ответ — **только** значение: без пояснений, единиц и кавычек. `exact_str` может учитывать регистр, поэтому сохраняем написание из базы.

## 3. Экономика токенов и стратегия

**Стоимость вызова = выходные токены + входные / 10.** Рассуждения (reasoning) считаются выходными, кеш не учитывается.

Что из этого следует:
0. **Сначала детерминированные решатели** (`harness/fastpath/`). Организаторы разрешили решать без LLM, а при равенстве баллов выигрывает меньший расход. Шаблоны 4 типов просты: решатель, который полностью распознал шаблон, даёт ответ за 0 токенов. Если сомневается — задача уходит агенту.
1. **Модели `-noreason` — основной вариант.** Рассуждения стоят как вывод, а это самая дорогая часть. Модель с рассуждениями включаем только как запасной вариант (прежде всего для `coding`).
2. **Входные токены в 10 раз дешевле выходных**, но при каждом шаге ReAct весь контекст отправляется заново, так что расход растёт квадратично от числа шагов. Выгоднее заранее собрать нужный контекст (без LLM) и решить задачу за 1–2 вызова, чем давать агенту «ходить» по файлам.
3. **За неверный ответ штрафа нет**, теряются только токены. Каждая попытка должна быть дешёвой. От задачи отказываемся рано, если видны признаки невыполнимости.
4. **Баллы случайны.** Порядок решения: `reward × P(успех) / ожидаемая_стоимость`, жадно.
5. **Ничья решается в пользу меньшего расхода**, поэтому даже после всех решённых задач лишних вызовов не делаем.

## 4. Архитектура харнесса

```
run_agent.py --tasks-dir /data/tasks [--out FILE]
  │
  ├─ 1. Загрузчик ── читает 100 × task.json, размеры workspace, список файлов
  ├─ 1.5 Быстрый путь (без LLM) ── шаблонные решатели harness/fastpath/, 0 токенов
  ├─ 2. Предпроверки (без LLM) ── признаки невыполнимости, тип задачи, сбор контекста
  ├─ 3. Оценщик ── прогноз стоимости в токенах и P(успех) для каждой задачи
  ├─ 4. Планировщик ── очередь по reward·P/стоимость, 5 воркеров, учёт бюджета и времени
  ├─ 5. Решатель (openJiuwen) ── промпт под тип задачи, мало шагов, сначала noreason
  ├─ 6. Проверка (без LLM) ── прогон unittest, формат int/str, sanity-check
  └─ 7. Запись ── answer.txt сразу после решения + файл решений после каждой задачи
```

### 4.1 Загрузчик
- Обходим `--tasks-dir`, читаем `task.json` и собираем признаки: тип, длина инструкции, число и размер файлов, число тестов и т.п.
- Задачи неизвестного типа тоже не пропускаем: для них есть общий промпт.

### 4.2 Предпроверки и сбор контекста (0 токенов)
- `search`: ищем `grep`-ом имя или компанию из вопроса. Нет совпадений или есть неоднозначность — подозрение на невыполнимость. Найденные файлы целиком кладём в промпт.
- `data_analysis`: проверяем, есть ли такой товар и такие колонки, лежат ли месяцы в диапазоне 1–12. В промпт идут заголовок CSV, 3 строки и число строк.
- `coding`: прогоняем тесты заранее. В промпт — `mylib.py`, тесты и вывод прогона.
- `math`: в промпт — только текст условия.
- Организаторы разрешили решать без LLM, поэтому то, что полностью распознаётся шаблоном, решает быстрый путь
  (`harness/fastpath/`, эталон — `data_analysis.py`). Предпроверки нужны для того, что быстрый путь не взял.

### 4.3 Решатель на openJiuwen
- Используем `ReActAgent` из `openjiuwen.core.single_agent` и shell-инструмент из `openjiuwen.core.sys_operation`. Рабочая папка — `workspace/` задачи. Для `math` создаём временную папку в `/tmp`.
- Короткий системный промпт и минимум описаний инструментов: схемы инструментов тоже входные токены, их размер нужно измерить.
- Лимит шагов по типу: 2–3 для `math`, `data_analysis` и `search`, до 5 для `coding`.
- Вывод инструментов обрезаем (например, до 2000 символов).
- Эскалация модели: `qwen3.6-35b-a3b-noreason` или `qwen3.8-27b-noreason` (выбрать по замерам) → при провале проверки один раз модель с рассуждениями → сдаёмся.
- Расход считаем сами по полю `usage` каждого ответа: `out + in/10 + reasoning`. Проверить, где прокси или NeuralDeep возвращает reasoning-токены.

### 4.4 Проверка без LLM
- `coding`: `python3 test_mylib.py` должен вернуть код 0. Плюс защита: файл с тестами не изменён (сравнить хеш).
- `exact_int`: ответ — целое число. Для `math` и `data_analysis` можно попросить модель вывести выражение или код и пересчитать его самим.
- `search`: ответ должен буквально встречаться в одном из файлов `kb/`.

### 4.5 Запись результатов (обязательно после каждой задачи)
- `answer.txt` пишем атомарно (временный файл → `rename`) **только** в `/data/tasks/<id>/answer.txt`, рядом с `task.json`.
  Агент сам `answer.txt` не пишет, а если всё же создал его в `workspace`, харнесс его удаляет.
- Невыполнимая задача (агент ответил `INFEASIBLE`, решатель вернул `infeasible`, тесты coding не прошли) — **файл не создаём**.
- Файл решений: если передан `--out` или задана переменная `OUT`, перезаписываем его после каждой задачи (JSON `{task_id: answer}`).
- При ошибке прокси (бюджет кончился, отказ в доступе) и при приближении конца часа всё уже записано, воркеры останавливаем спокойно.

### 4.6 Планировщик
- Бюджет читаем из `BUDGET` (без него — 100000), остаток считаем сами: прокси его не сообщает.
- **После исчерпания бюджета прокси перестаёт отвечать, а запуск принудительно завершают**, поэтому пересекать бюджет
  нельзя ни на один вызов. Перед вызовом резервируем его худшую стоимость (оценка входа + `max_tokens`), после вызова
  снимаем резерв и пишем факт (`harness/meter.py`, `harness/llm.py`). Если мешают только резервы параллельных вызовов —
  ждём. Плюс потолок на задачу (`HARNESS_TASK_TOKEN_CAP`). Проверено: с `BUDGET=5000` решены все 8 примеров за 1744 токена.
- Порядок: сначала все задачи быстрого пути (бесплатно), затем агент по убыванию `reward / оценка стоимости`.
- 5 параллельных воркеров. Учитываем лимит процессов (`--pids-limit 512`) и квоты NeuralDeep при разработке: 60 запросов в минуту, 16 потоков.
- Сторож времени: прогон должен закончиться заранее, примерно на 55-й минуте. Таймаут на каждую задачу и на каждую команду shell.
- Если известны бюджет и текущий расход, не берём задачу, оценка стоимости которой больше остатка.

## 5. Невыполнимые задачи (15–25% финального набора)

В примерах их нет, гипотезы нужно проверить на своих генерациях:

| Тип | Возможные признаки невыполнимости |
|---|---|
| `search` | Человека или компании нет в `kb/`; цепочка обрывается (нет файла работодателя, нет поля `Headquarters`); два человека с одинаковым именем |
| `data_analysis` | Нет такого товара или колонки; месяц вне 1–12; нет файла. **Осторожно:** товар есть, но продаж 0 — это верный ответ `0` |
| `math` | Не хватает данных; деление на 0 складов; противоречивые условия |
| `coding` | Тесты противоречат друг другу; тест требует функцию с неопределённым поведением; нужна сеть или файлы вне папки |
| Любой | Инструкция требует сети, внешних файлов или того, что запрещено «work only inside the current directory» |

Определение организаторов: невыполнимая задача — та, которую **нельзя точно решить при имеющихся данных**.
Для неё **не создаём `answer.txt`**. Баллов за пропуск нет, так что выигрыш только в сэкономленных токенах.

Порядок действий: предпроверка или быстрый путь (0 токенов) → если сработали, задачу пропускаем без вызова LLM.
Если признак обнаружился уже во время решения (модель ответила `INFEASIBLE`, тесты не проходят), обрываем решение сразу.
Примеры невыполнимых задач для проверки — `tasks_custom/` (по одной на тип, поле `"feasible": false`).

## 6. Тренировочный набор, траектории и оценщик

1. **Генератор задач** по 4 шаблонам с вариациями: длина цепочки в math, размер CSV, глубина поиска, число багов и тестов. Отдельно делаем невыполнимые варианты из раздела 5. Цель — 300–500 задач со своими `expected`.
2. **Локальный оценщик**, повторяющий проверки организаторов: `exact_int`, `exact_str`, `unittest` (свои «скрытые» тесты для coding).
3. **Траектории**: для каждого прогона логируем задачу, модель, шаги, токены (in/out/reasoning), время и результат. Храним в `trajectories/` в формате jsonl. Регламент требует описать их в README.
4. **Оценщик стоимости**: сначала таблица средних по типам, затем регрессия или градиентный бустинг по признакам из 4.1. Цель — `E[стоимость]` и `P(успех)`. Классические методы разрешены. LLM на собранных ответах **не обучаем**: это запрещено памяткой (п. 2.4).
5. **Оценщик будут проверять отдельно.** Организаторы дадут новые запросы, расход по ним нужно предсказать **до запуска**.
   Метрики (MAE, относительная ошибка, штраф за недооценку) опубликуют позже. Поэтому оценщик — отдельный модуль,
   который работает только по тексту задачи и её файлам, а в траекториях всегда пишем прогноз (`estimate`) рядом с фактом (`cost`).
   Готовых трасс и размеченного набора организаторы не дадут — всё собираем сами.

## 7. Docker: на чём легко споткнуться

- Корень файловой системы только для чтения:
  - `PYTHONDONTWRITEBYTECODE=1`;
  - логи, кеши и рабочие папки openJiuwen — только в `/tmp` (`HOME=/tmp`, проверить, куда пишет openJiuwen);
  - проверить, что ничего не пишется в `/app` и `site-packages`.
- **Сети нет**, поэтому всё нужное кладём в образ:
  - `tiktoken` при первом использовании скачивает словари — заранее положить их в образ (`TIKTOKEN_CACHE_DIR`);
  - то же для токенизаторов `transformers`, если openJiuwen их загружает;
  - проверить запуском без сети.
- `python3` в контейнере обязателен: его вызывают сами задачи. Берём образ вроде `python:3.12-slim-bookworm` с зафиксированным тегом или digest.
- Все версии зафиксировать (`requirements.txt` с `==`). Проверить размер образа (меньше 4 ГБ) и время сборки (меньше 1000 с).
- Агент выполняет shell-команды: запускаем их с `cwd` в папке задачи, с таймаутом, без доступа к соседним задачам. Это заметит и LLM-проверка безопасности. Никакого обфусцированного кода и обращений к адресам, кроме `LLM_BASE_URL`.
- Свой скрипт `scripts/run_dev.py` с **точно такими же флагами** `docker run` и локальной папкой задач. Гонять его перед каждым важным коммитом.

1. **Инфраструктура**: Docker, `run_agent.py`, запись ответов, учёт токенов, `scripts/run_dev.py`, время сборки.

3. **Данные и ML**: детерминированные решатели (`harness/fastpath/`), генератор задач, предпроверки невыполнимости, оценщик стоимости, планировщик.

Ключи и квоты NeuralDeep: у каждого свой код приглашения и свой ключ. Один ключ одновременно можно использовать максимум с **2 IP-адресов**, иначе он блокируется на 60 минут. Базовый адрес для разработки: `https://api.neuraldeep.ru/v1`. Ключи в репозиторий не коммитим.

## 10. Главные риски

- **Не пройти отборочный прогон** (2 задачи). Базовый путь «решить простую задачу» должен быть железобетонным, а ответы — записываться сразу.
- **Другие формулировки в финале** («новые и другие вопросы», встреча 09.11). Быстрый путь и правила невыполнимости
  настроены на примеры и наш генератор, в финале они должны молчать, а не ошибаться: неверный ответ быстрого пути или
  ложное «невыполнима» стоят задачи, которую решил бы LLM.
- **Сломаться на read-only и без сети** (кеш tiktoken, логи openJiuwen). Проверять запуском с флагами регламента.
- **Перерасход на «вечных» задачах.** Жёсткие лимиты шагов и токенов на задачу, ранний отказ.
- **Не уложиться в 1 час.** Таймауты на вызовы и команды, сторож времени.
- **Упереться в лимиты NeuralDeep** (60 запросов в минуту и **3 одновременных запроса на аккаунт**). Свой ограничитель:
  50 запросов в минуту, не больше 2 одновременно, повторы при 429/5xx (`harness/llm.py`); openJiuwen сам не повторяет (`max_retries=0`).
- **Утечка ключа в репозиторий.** `.gitignore` для `.env`, ключ только через переменные окружения.
